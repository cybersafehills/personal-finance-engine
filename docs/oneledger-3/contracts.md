# OneLedger 3.0 — API contracts (S1, DRAFT — freeze after owner review)

Conventions follow `docs/mobile-api.md`: bearer Supabase token, `getUser` + MFA aal2, flag → 404 when off, `no-store`, rate-limited, bodies never logged, JSON. **The spec's candidate routes are adapted, not duplicated:** existing `/api/v1/{accounts,transactions,categories}` (developer API, API-key auth) are untouched; new app-facing routes go under `/api/mobile/*`; web uses server components calling the same `lib/insights` functions directly.

Common: money = `{ "amount_minor": "string-int64", "currency": "RWF" }` (string to stay JSON-safe for bigint). Timestamps ISO-8601 UTC plus `tz` echo. Pagination: opaque `cursor`, `limit` ≤100, stable sort `(effective_at desc, id desc)`. Errors: `{ok:false,error:<code>,message}` with codes `invalid_request|unauthorized|mfa_required|forbidden|not_found|rate_limited|conflict|server_error`. Scope param: `workspace_id` (validated against membership; default personal).

## Insights (flag INSIGHTS_CENTER_ENABLED)
`GET /api/mobile/insights/overview?from&to&account_id[]&category&counterparty_id&type&currency`
→ `{ period:{from,to,tz}, currency, money_in, money_out, net, counts:{in,out}, transfers_excluded:{amount,count}, pending:{amount,count}, by_category:[{category,amount,pct,drilldown}], by_account:[…], top_counterparties:[…], compare:{prev_period, delta}, freshness:{computed_at, latest_txn_at}, notes:[ "estimate"|"incomplete_data" codes ] }`
Every `drilldown` = a filter object accepted verbatim by `GET /api/mobile/transactions`.
`GET …/insights/trends?granularity=day|week|month` → series of `{bucket_start, in, out, net}`.
Multi-currency: one block per currency; no silent conversion.

## Accounts / balances (flag BALANCE_PROVENANCE_ENABLED)
`GET /api/mobile/accounts` → `[{id, alias, provider, masked_identifier, currency, visibility, balance:{status:"confirmed|estimated|stale|unavailable", amount?, as_of?, basis}, ingestion_state}]`
`POST /api/mobile/accounts/{id}/reconcile` body `{observed_amount_minor, as_of, note?}` + `Idempotency-Key` → creates a manual `balance_observation` + audit event; returns new status.

## Transactions
`GET /api/mobile/transactions` (filters = insights filters) ; `GET /…/{id}` (sensitive fields like Cash Power token returned only to roles with capability `view_sensitive_tokens`, else `redacted:true`); `PATCH /…/{id}/classification` `{category?, counterparty_id?}` → triggers aggregate invalidation (projections are computed on read in v1, so no rebuild needed).

## Counterparties (flag COUNTERPARTIES_ENABLED)
`GET /counterparties?q&kind&period` → `[{id, display_name, kind:"person|merchant|unknown", confidence:"user_confirmed|high|low", sent, received, net, count, first_at, last_at}]`
`GET /counterparties/{id}` (+ transactions via drill-down) ; `PATCH /counterparties/{id}` `{display_name?, kind?}` ;
`POST /counterparties/merge` `{survivor_id, merged_ids[]}` and `POST /counterparties/split` `{counterparty_id, identifier_ids[]}` — both write `counterparty_merge_events` and are reversible (`POST /counterparties/merge/{event_id}/undo`).
Same display name alone never auto-merges; auto-grouping only on normalised identifier (e.g. `2507XXXXXXXX`, merchant code).

## Payment requests (flag PAYMENT_REQUESTS_ENABLED; Stage 1 only)
`POST /payment-requests` `{amount_minor, currency, recipient_destination, reference?, expires_at}` + Idempotency-Key → `{id, public_url, status:"open"}` (token 128-bit random, only hash stored).
`GET /payment-requests`, `GET /payment-requests/{id}`, `POST /payment-requests/{id}/cancel`.
Public (no auth, rate-limited, no PII beyond need): `GET /r/{token}` → `{amount, currency, reference, recipient_display, expires_at, status, disclaimer:"unverified"}`. Never returns workspace/user data. Status set: `open|cancelled|expired|marked_paid_by_owner|matched` — `matched` only via a human-confirmed link to a real incoming transaction; link-open or payer claim never changes status.
Fee estimates (flag FEE_CALCULATOR; implemented, see `s10-fee-calculator.md`): `GET /api/mobile/fees/estimate?amount&currency[&type][&network][&provider][&workspace_id]` → `{workspace_id, computed_at, amount_minor, currency, transaction_type, history:{status:"estimate"|"not_enough_history"|"no_history", min_minor, max_minor, typical_minor, count, …}, published:null|{network, has_schedule, fee_type, estimate:{status:"exact"|"range"|"upper_bound"|"not_computable"|"not_in_effect", …}, source_label, source_url, effective_from, effective_to, limit_warnings[]}, provider_tariff:null|{provider:{slug,name}, has_tariff, rows:[{recipient_scope, schedule_state, estimate, source_label, source_url, effective_from, effective_to, verified_at, note}]}, disclaimer}`. Amounts are decimal strings. History (your own past fees) and the published schedule are reported separately, never blended; a tiered/unknown/varies fee returns no number, never 0; no split suggestion is ever returned.

## Pay splits (flag PAY_SPLITS_ENABLED + ASSISTED_PAY_ENABLED; see `docs/pay-splits.md`)
A payment sent as several transfers. Each part is an ordinary draft `payment_intent` the person hands off themselves, one at a time; OneLedger never moves money. Same bearer guard (second factor complete) as the other `/api/mobile/pay/*` routes; same code as the web actions (`lib/pay/splits/service.ts`). The app never supplies parts: the server recomputes the offer from the amount. All money is integer minor units (RWF has no decimals); offer amounts are digit strings. Assisted pay off, or splits off for `start|next|stop` → `403 feature_disabled`.
`POST /api/mobile/pay/splits/offer` `{paymentType:"pay_person"|"pay_merchant", amountMinor, networkSlug?:"ekash", sourceAccountId?, recipientMsisdn?}` → `{offer: null | {kind:"capacity"|"fee_saving", networkSlug, currency, totalMinor, parts:[{index, amountMinor, feeMinor|null}], singleFeeMinor|null, plannedFeeMinor|null, savingsMinor|null, feeBasis:"verified_tariff"|"published_maximum"|"none", capacityMinor|null, source:null|{label,url,asOf}, threshold|null}}`. Read-only (a POST so a phone number never lands in a URL log). `offer` is null when the payment goes as one transfer, or splits are off. eKash: an offer exists **only when the amount exceeds** the network's per-transaction capacity (fallback RWF 10,000,000 / fee 20 unless `route_limits`/`route_fees` say otherwise); fee is a published ceiling, not a prediction. `fee_saving` (MTN to MTN) needs the user's opt-in and a **verified** tariff, so it never appears until one is loaded. Part amounts and fees are estimates, never guarantees; institutions may enforce lower limits.
`POST /api/mobile/pay/splits/start` `{…create-intent body (paymentType, amountMinor, idempotencyKey (uuid), recipientMsisdn|merchantCode, sourceAccountId?), networkSlug?}` → `{planId, intent}` where `intent` is part 1 as a `MobileIntent` (state `draft`). The request id makes a retry the same plan and the same part. `422 no_split` when the amount needs no split; `422 invalid_account` when the account isn't one of the active Space's own.
`POST /api/mobile/pay/splits/{id}/next` `{}` → `{planId, index, intent}`: the next part as a draft. Allowed only once the previous part is `successful` (provider-verified or manually confirmed); otherwise `409` with `error` ∈ `waiting` (previous part not settled), `blocked` (the last part failed or expired), `stopped`, `complete`. Keeps SMS reconciliation unambiguous. Settle each part with the existing `/pay/intents/{id}/handoff` and `/settle`.
`POST /api/mobile/pay/splits/{id}/stop` `{}` → `{planId, stopped:true}`: no more parts; unsent drafts are cancelled, settled parts are left alone. Repeatable.
`GET /api/mobile/pay/splits/{id}` → `{plan:{id, kind, networkSlug, currency, totalMinor, plannedPartsMinor[], singleFeeMinor|null, plannedFeeMinor|null, feeBasis, stopped, parts:[{index, intentId, amountMinor, state}], next:{status:"ready"|"waiting"|"blocked", index, amountMinor} | {status:"complete"|"stopped"}, remainingMinor, canSendRemaining}}`. A payment that is one part of a plan carries `splitPlanId` and `splitIndex` on the intent (null otherwise); `GET /api/mobile/config` carries `paySplits`.
`GET /api/mobile/pay/splits/preferences` → `{preferences:{feeSavingEnabled, threshold}, thresholds:[{value:"any"|"balanced"|"bigger", minSavingPerExtraPartMinor}]}`. The three levels are shown as **Every Franc** (any saving), **Worth It** (at least 100 RWF per extra transfer; the default) and **Big Wins** (at least 500 RWF); the app reads the figures from `thresholds` rather than hard-coding them; `POST` the same two fields (`feeSavingEnabled` must be an explicit boolean) → `{preferences}`. Fee-saving (MTN to MTN) is **off until the person turns it on**; over-capacity eKash amounts do not depend on it.
`GET /api/mobile/pay/splits/savings` → `{report:{generatedAt, currency:"RWF", periods:[{key:"24h"|"7d"|"14d"|"30d"|"90d"|"365d"|"all", savedMinor, wouldHavePaidMinor, paidMinor, plans, transfers}] (all seven, in that order), inProgress:{plans, expectedSavingMinor}, recent:[{planId, completedAt, totalMinor, savedMinor, transfers}] (latest 5)}}`. What Save On has saved in transfer fees: for each fee-saving plan, the fee as one transfer minus the fee as parts, both from a verified tariff. A saving counts **only once every part of the plan is settled** (provider-verified or confirmed by the person) and is dated by when the last part settled; a plan still being sent is `inProgress` (the saving it is expected to make), and a stopped plan or an over-the-eKash-limit plan counts for nothing. Computed live (`save_on_report`), read-only, under the caller's RLS. Estimates: the provider shows the final fee.
Fee data (Save On): MTN person-to-person and MTN-via-eKash fees come from the verified tariffs loaded from MTN's own page (`docs/oneledger-3/tariff-sources/`). For an MTN payer over eKash `feeBasis` is `verified_tariff` (RWF 20 per transfer, exact); otherwise the network's published ceiling (`published_maximum`). Airtel has no published person-to-person table, so it never gets a fee-saving offer.
Errors: `404 not_found` (unknown or not yours), `422 invalid_request|invalid_account|no_split|could_not_prepare`, `409 waiting|blocked|stopped|complete|not_allowed`. Not in the API (web only): "send remaining as one" for fee-saving plans, and the fee-saving preference.

## Contract enforcement
- JSON Schema files in `docs/oneledger-3/schemas/` (one per response) are the source of truth; a Deno test validates handler outputs against them and mobile client types are generated/checked from them in CI.
- Mocks used before APIs exist are labelled `__mock` in the response and fail the release checklist.

# S5 — Payment requests, Stage 1 (2026-11-15)

**Non-custodial.** OneLedger never holds, moves or initiates money. Stage 2 (provider deep links) and Stage 3 (payment execution, callbacks) are **not built and remain gated** on provider terms, legal/regulatory review and your approval.

**Delivered (database + pure library; no route, UI or flag yet):**

- `web/lib/payment-requests/payment-request.ts` (+7 tests): token generation/hashing, link/QR builder and strict parser, input validation, state machine, payer-facing wording.
- Harness: 35 S5 assertions; counters re-based (tables 136, authenticated table grants 175, authenticated function EXECUTE 130, **anon function EXECUTE 2**).

**Verified:** full `run_migration_tests.sh` on disposable PostgreSQL 17 — 645 passed, 0 failed (stacked on S3/S4). `deno test web/lib` passes. Not run: Playwright, CI, any Supabase apply, any HTTP-level test (there is no route).

## Guarantees (enforced in the database, tested)
- **Token:** generated by the app (256-bit); the DB only ever receives/stores its SHA-256 hex digest — never the token. Public resolver takes the digest.
- **Never falsely "paid":** opening a link or a payer's claim changes nothing. Only two attested end states exist: `marked_paid_by_owner` (explicitly `verified:false`) and `matched`, which requires a human to link a **settled, incoming, same-currency, exactly-equal-amount** transaction in the **same workspace**, linked to at most one request. The DB refuses `matched` without a linked transaction.
- **Public resolver minimum:** returns status, amount, currency, recipient display name, reference, expiry and — only while open and unexpired — the destination. No workspace, owner, id, transaction or history. Unknown/malformed digests return nothing.
- **Validation server-side:** amount 1…10¹², currency RWF/USD/EUR, Rwandan mobile number (normalised) or 4–8 digit merchant code, no control characters, expiry between +1 minute and +90 days.
- **Abuse limits:** 30 creations/user/hour, 200 open requests/workspace; idempotent create by (workspace, key).
- **Authz:** member+ creates; creator or workspace owner cancels/marks/links; viewers and other workspaces refused; no direct table writes.
- **Audit:** every transition writes `payment_request_events` and `space_audit_events`.
- **Expiry** is derived at read time (no cron to fail).
- **QR/link safety (library):** the only encodable form is `https://<our origin>/r/<64-hex>`; the parser rejects http, other/look-alike hosts, userinfo, ports, query, fragment, extra path, wrong case.

## Not built / needs you
1. **The `/r/[token]` page and its API route** (hash the token, call the resolver, render `payerFacingLabel`). **The route must rate-limit by IP and send `no-store`/`noindex`** — the database cannot see IPs. Next.js in this repo has breaking changes (`web/AGENTS.md`); read `node_modules/next/dist/docs/` first. Needs `PAYMENT_REQUESTS_ENABLED` + allowlist flag (pattern as other features).
2. **Owner UI + mobile screens** to create/share (QR via existing `lib/qr.ts` `qrSvg`), cancel, mark paid, link a transaction.
3. **Idempotent retry cannot re-issue a token** (the DB never has it): the client must reuse its own token on retry, or cancel and recreate.
4. Linking only works for **RWF** requests today (transactions are RWF-only); USD/EUR requests can be created but never matched.
5. A request whose matched transaction is hard-deleted would violate its own check and fail loudly rather than silently downgrade (transactions aren't hard-deleted by the app; workspace erasure cascades). Confirm account-erasure/export coverage for the new tables before rollout.
6. Phishing risk remains inherent to any "pay this number" page: the recipient shown is the **owner's own text**, not verified. The payer-facing copy must keep "not verified by OneLedger".
7. Legal/regulatory review (Rwanda) is still required before enabling beyond your own allowlist; no compliance claim is made.

## S5b — public page `/r/[token]` (built; PR stacked on S5)
**Delivered:** `web/app/r/[token]/page.tsx`; `web/lib/payment-requests/{resolve,public-view,rate-limit}.ts` (+9 tests, 16 in the folder); `/r` added to `proxy.ts` PUBLIC_PATHS; `next.config.ts` headers for `/r/:token`.
- **Dark** unless `PAYMENT_REQUESTS_ENABLED=true` (renders the app 404 otherwise). **Not enabled anywhere** — set it only after review.
- Resolution uses the **anon** key and the SHA-256 digest only; the raw token never leaves the web process (verified: the stub RPC server saw 64-char digests only). Malformed tokens never reach the network.
- Per-IP limit 30 page loads/minute (in-memory, per instance, resets on deploy, bounded memory) — same best-effort model as `/verify`. The 256-bit token is the real defence.
- Headers on `/r/:token` (verified on a production build): `Cache-Control: no-store, max-age=0`, `X-Robots-Tag: noindex, nofollow`, `Referrer-Policy: no-referrer`; page also sets `robots` + `referrer` metadata.
- Page content: amount, requested-by name, reference, validity, and (open only) the number/merchant code, always with "not verified by OneLedger" wording and a "check the name and number" warning. Cancelled/expired/paid-states show no destination. The mapper refuses malformed rows (unknown status/currency, non-positive amount, open without a valid destination) rather than render them.

**Verified:** unit tests; full `tsc` clean (after `next typegen`); `next build` succeeds; against a local stub of the Supabase RPC on a dev server and a production `next start`: open/cancelled/matched render correctly, unknown/malformed tokens give the 404 page, rate limit trips at the 31st request from one IP and not for another, flag-off gives 404. **Not verified:** against a real Supabase (the stub emulates the RPC contract only; the SQL itself is covered by the 645 migration tests), real browsers/devices, CI, Playwright, production deploy.

**Known limitations**
- A real **HTTP 404 status is not returned** for unknown tokens: the app-wide `app/loading.tsx` makes Next stream a 200 with the not-found UI (same as `/verify`). The `noindex` header still applies.
- The limiter is per instance; on multi-instance Vercel the effective limit is higher. A shared limiter (the `api_rate_buckets` table or Edge Config) would be needed for a hard cap.
- No JSON API variant of the resolver (the page is the only consumer today).
- Amounts render via the existing `formatMoney` (e.g. "RF 5,000").
- Still not built: owner UI/mobile screens to create/share/cancel/mark/link, and the flag allowlist.

## S5c — owner screens (built; PR stacked on S5b)
**Delivered (web only):** `/pay/requests` (list), `/pay/requests/new` (create + one-time share panel with copy / native share / QR), `/pay/requests/[id]` (details, history, link-a-payment, mark paid yourself, cancel); server actions in `app/pay/requests/actions.ts`; components `PaymentRequestForm` / `PaymentRequestActions`; `lib/payment-requests/owner.ts` (+ `owner-data.ts`), 6 more tests (22 in the folder).
- **Opt-in:** needs `PAYMENT_REQUESTS_ENABLED=true`; optional `PAYMENT_REQUESTS_WORKSPACE_ALLOWLIST` (comma-separated workspace ids) restricts creation/management (the public `/r` page checks only the global flag so shared links keep resolving). Off by default; not enabled anywhere. Also needs `SITE_URL` set to a bare **https** origin or creation refuses ("Sharing links isn't configured").
- **Token is shown once.** The server generates it (256-bit), stores only the digest, and returns the URL in that single action response; the detail page can't re-show it. A double-submit (same idempotency key) returns the original request with "link can't be shown again". Losing the link = cancel and recreate.
- Server actions re-check session, active workspace, flag and allowlist on every call; `requireMfaForSensitiveAction` guards create, mark-paid and link (users with a verified factor must be at aal2; users without MFA are unaffected, per existing policy). RLS and the RPC role checks remain the authority. Error text is mapped to fixed friendly messages (raw DB text never shown).
- "Link the payment" lists only settled incoming transactions of exactly the request amount that no other request has claimed (RWF only); marking paid is a confirm-twice action worded as the owner's own, unverified statement.
- Not in main navigation: reach it at `/pay/requests` (nav needs capability plumbing through AppShell/MoreSheet — deliberately left out of this slice).

# OneLedger web / Android / iOS parity matrix

Baseline: **2026-11-18, local main `36ad79b`**. Final GitHub metadata confirms #281 merged remotely as `91baf55`; its balance-visibility fix is absent from this local baseline and deployment remains unknown. #282–#287 are open. Read with [current-state audit](ONELEDGER_CURRENT_STATE_AUDIT.md), especially F01–F16, test results and deployment limits. Android here means the full Expo application; the legacy companion is assessed separately below.

**Implemented** = a bounded code path with logic/mutation and relevant tests was found, not just a route. **Partial** = a missing action, inconsistent result, browser dependency or unverified integration remains. **Broken** = a concrete source-level defect affects this capability in the stated scenario. **Missing** = no native implementation of the named action was found. None means production/device verified. Native shared-source evidence applies separately to each platform; no iOS or Android runtime was executed. Broad capabilities remain partial even when many subflows exist.

Paths are relative to repository root. Abbreviations: **W** `web/`; **M** `oneledger-mobile/src/`; **S** `supabase/`; **E2E** `web/e2e/`; **DS** shared design-system components. Tests named below exist; only suites recorded in the audit were run. Every row inherits the requirement for loading, empty, permission-denied, retryable error, success and stale-data verification in its acceptance journey.

## Legacy Android companion disposition

`android/` provides pairing/QR, notification matching, credential storage, Room queue, WorkManager uploads and health via Compose. These responsibilities have already been ported into `oneledger-mobile/modules/oneledger-capture`; do not port the full web app into this legacy project or create a separate Swift product UI.

Keep the companion available as a reference/rollback artifact until upgrade testing proves the Expo package, signing identity, versionCode, notification service, encrypted preferences and existing queue behavior. Identical preference names and package names are evidence to investigate, not proof that Room/key/worker migration is safe. Acceptance: existing companion install with pending captures → upgrade or documented reconnect → no double sends, lost pending messages or leaked credentials; both same-key and different-key installation paths addressed. No removal of legacy project is authorized by this assessment.

## Common verification contract

Use one golden dataset across the web and independent Android/iOS runs: two Spaces, two members plus viewer, shared/private sources, multiple wallets, RWF/USD/EUR, fees, failed/pending/reversed/merged rows, own transfers, category splits, month/day boundaries and >1,000 transactions. Assert stored facts and headline/drill-down agreement before screenshots. Payment acceptance requires distinguishing copied/dialed, user-marked and server-evidence-matched states. Every browser fallback is explicitly labelled and preserves scope without sharing credentials in URLs.

Native list screens and parsers have substantial unit coverage, but mocks cannot establish RLS, native permissions, real bearer identity, SQLCipher linkage, native sheet gestures or background execution. The audit's successful pure/migration suites therefore do not turn these partial rows into verified end-to-end parity.

## Native goal management follow-up — 2026-11-19

Native Goals now supports creating and archiving goals for users with `goal.manage`. Contribution history offers removal to managers and the person who entered the contribution. The native archive view preserves readable history. Removal changes goal progress and leaves linked ledger transactions in place. Participant editing remains on the web.

Creation retries reuse the same goal ID while the form is open. If the app closes before the response arrives, review the refreshed goal list before creating the goal again. These online actions reuse existing database policies and require no additional migration.

## Native Insights forecast follow-up — 2026-11-19

Insights now offers a cash-flow forecast on mobile for eligible RWF wallets using the same server model as the web. The wallet selection and 7-, 14-, or 30-day horizon apply to the forecast. Historical Insights periods apply to the existing retrospective totals. The forecast shows the source balance date, scheduled and estimated closing balances, and the no-new-income scenario when the model estimates income.

Server reads page the applicable history and exclude own transfers, merged duplicates, unfinalized transactions, and other currencies. Only unpaid RWF bills in the selected Space contribute to its default forecast wallet. The server refuses histories over its coverage limit. The feature is online and opt-in, and depends on the existing financial activity view migration. Signed HTTP and physical device checks remain open.

## Native budget creation and activation follow-up — 2026-11-19

Budget managers can create drafts in Plan or Budget, edit their allocations, review server-calculated monthly targets, and activate a saved draft. The native form captures currency, dates, and one of the five existing income frequencies. It requires four percentages totaling 100% on creation. Older incomplete drafts can still be opened and repaired before activation.

Draft creation is atomic and uses a request ID stored securely on the device before submission. Activation checks the reviewed revision and the existing one-active-budget-per-Space-and-currency rule. Both operations require a connection. Native income editing, archiving, and rollover remain separate slices.
